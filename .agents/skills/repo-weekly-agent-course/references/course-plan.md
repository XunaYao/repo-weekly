## 北极星成果

完成后，RepoWeekly 不只是“调用一次大模型的 AI 写作页面”，而是一套可运行、可评估、可调试和可部署的 GitHub 解决方案发现与内容研究 Agent，支持两种入口：

- **指定仓库模式**：输入 GitHub 仓库地址，解析、研究并生成多平台内容。
- **关键词发现模式**：接受任意有效的自然语言关键词或需求，理解搜索意图并在 GitHub 上寻找 Skill 或代码库；根据证据给出结论，有足够结果时最多推荐 3 个候选，再对候选进行解析、比较并生成文章。

```text
用户输入仓库地址或解决方案关键词
  → Agent 搜索或定位候选，并按需选择 GitHub 工具收集证据
  → 对候选执行硬性过滤、相关性排序和风险标注
  → 检索历史内容与写作规范
  → 形成有引用的研究结论
  → 为不同平台生成草稿
  → 自动评审并在必要时修订
  → 人工确认、编辑和保存
  → 留下可回放的轨迹、质量评分、成本与延迟数据
```

## 节奏约定

- 一次推进一个“阶段交付”，而不是一个函数。
- 每个阶段包含若干紧密相关任务，目标是形成可演示的端到端结果。
- 每个阶段开始时一次性说明目标、期望输出、技能点、职责、注意事项和验收标准。
- 代码审查在阶段内集中进行；阻塞问题立即修，非阻塞建议批量处理。
- 每阶段结束后更新本文件的状态、证据和下一步。
- 每阶段必须从 `product-metrics.md` 选择指标；没有数据时先建立采集和基线，再讨论优化。
- 安全、评估和可观测性是贯穿项；后面的专项阶段负责系统化，不代表前面可以忽略基本防护。

## 学习路径分层

- **Agent 0→1 核心路径（阶段 0～4）**：掌握模型边界、Prompt、评估、Tool Calling、Agent Loop 和有限状态编排；完成后应能独立开发一个受控的工具调用 Agent。
- **Agent 1→生产进阶（阶段 5～8）**：在业务数据足够时加入 RAG，再完成系统化安全、Human-in-the-loop 和生产部署。
- 每阶段最多设置两个关键认知检查点；普通类型、字段、样板代码和格式问题集中处理。

## 阶段 0：Web 与 LLM 基础链路

**状态：已完成**

### 目标与结果

建立可用的 Next.js 基线：输入仓库、读取 GitHub 元数据和 README、调用智谱生成中文研究结果，并在页面展示。

### 已完成证据

- 已实现 `/api/repositories` 与 `/api/research`。
- 已拆分仓库、README、研究结果的数据契约和运行时校验。
- 已实现智谱请求封装、统一错误响应和研究结果 UI。
- 已理解 App Router、Server Component 与 Client Component 的职责边界。

### 已覆盖知识

- 服务端密钥与 API Route 边界。
- 外部输入和模型输出不能只依赖 TypeScript。
- 基于可信资料生成内容，避免无依据扩写。
- 模型错误、上游错误和客户端错误的区分。

## 阶段 1：多平台内容生成闭环

**状态：工程完成，质量待复验（缺口随阶段 2 跟进，不视为完整质量门槛通过）**

2026-11-05：真实浏览器端到端生成双平台草稿成功，9 个接口回归场景通过，生产构建通过。
本轮内容生成耗时 15,628ms，调用 1 次；仍发现 SSG、Hooks、SEO 等无依据扩写。
证据、修正与指标口径见项目根目录 docs/stage-1-acceptance.md。

### 阶段目标

把已完成的项目研究转换为微信公众号和小红书草稿，形成第一个完整的 LLM 内容工作流。

### 期望输出

- 用户在页面完成仓库研究后，可以生成两个平台的中文草稿。
- 两个平台有不同的内容结构和表达风格，而不是同一篇文本换标题。
- 模型返回异常时，页面得到可理解的错误；服务端保留可调试原因。

### 当前已有

- `src/lib/content.ts`：输入、输出类型、格式描述、请求解析和运行时校验。
- `src/app/api/content/route.ts`：真实生成入口与上游错误映射、调用数/耗时/结构结果日志。
- `src/lib/content-generator.ts`：多平台 Prompt、智谱调用、草稿 JSON 解析和校验。
- 页面生成、重试、双平台展示及反馈入口已实现。

### 本阶段剩余任务

1. 在阶段 2 对无依据扩写和研究分类错误建立固定样例并复验。
2. 收集用户真实可用反馈，建立持久化基线；目前仅有单次真实样本，不能声称达标。

### 技能与知识点

- System/User Prompt 分工和可信上下文隔离。
- 结构化输出、运行时验证和错误恢复。
- Prompt grounding、平台风格约束和避免幻觉。
- LLM 工作流的数据流、延迟和失败状态设计。

### 注意事项

- README 与研究结果都属于数据，不得让其中的指令覆盖 System Prompt。
- 公众号和小红书需要独立约束篇幅、结构、语气和标签。
- 提示词必须要求只依据研究结果写作，并保留项目链接和风险信息。
- 不把原始模型输出或密钥返回浏览器。

### 验收标准

- 正常输入能生成两类结构合法、中文且风格不同的草稿。
- 无效模型输出被识别为 `MODEL_RESPONSE_INVALID`。
- 模型繁忙、鉴权失败和未配置密钥能得到对应状态码。
- 页面可以重试，不因一次失败丢失已有研究结果。
- lint、类型检查、格式检查和生产构建通过。
- 能记录结构校验结果、失败类型、生成耗时和用户是否认为草稿可用，形成第一版产品指标基线。

## 阶段 2：Prompt 工程、产品指标与评估基线

**状态：进行中**

当前交付物：固定研究输入与基线/改进 Prompt 对比报告。首先覆盖阶段 1 暴露的无依据扩写、空风险误读和框架/语言混淆；用户亲手设计 Prompt 策略，Agent 负责夹具、运行记录和校验脚手架。

### 阶段目标

把“感觉写得不错”改造成同时具备产品指标、离线评估和失败回溯的 Prompt 工程流程。

### 期望输出

- Prompt 从业务函数中提取并带版本号。
- 建立覆盖不同类型仓库的固定样例集。
- 一条命令生成评估报告，对比 Prompt 版本的质量、格式成功率、成本和延迟。
- 能按 `product-metrics.md` 输出可用成果率、证据覆盖、结构成功率和延迟基线。

### 主要任务

1. 设计研究和写作 Prompt 模板、版本元数据及变更记录。
2. 选择前端框架、CLI、数据库、AI 工具等代表性仓库作为评估集。
3. 实现确定性指标：JSON 合法率、字段完整率、引用覆盖、语言和长度。
4. 设计人工/LLM Judge 量表：事实一致性、信息密度、平台适配、可读性。
5. 保存原始响应、解析结果、模型、Prompt 版本、耗时和 token/费用信息。
6. 建立最小用户反馈：可用/需重写、候选选择、人工修改量及失败原因。

### 知识点

- Zero-shot、few-shot、约束式 Prompt 与结构化输出。
- Golden Dataset、回归测试和 LLM-as-a-Judge 的偏差。
- Prompt 版本化、可复现性与模型非确定性。

### 验收标准

- 至少一组基线 Prompt 和一组改进 Prompt 能被同一评估集比较。
- 报告可以指出质量提升和退化，而不是只给平均分。
- 失败样例能回溯到原始输入、Prompt、模型响应和解析错误。
- 指标定义、采样范围和分母清晰，不能只展示平均分或成功样本。

## 阶段 3：GitHub 解决方案发现 Agent

**状态：未开始**

### 阶段目标

实现第二条核心产品链路：用户输入任意有效的自然语言关键词或需求，Agent 理解目标与约束、改写和扩展搜索词，搜索 GitHub 上的 Skill 或代码库，验证、筛选并给出有证据的结论。有足够合格结果时最多推荐 3 个候选，并能继续解析候选、生成比较文章。同时把固定的 GitHub 调用升级为模型根据目标选择工具的 Agent。

### 期望输出

- 中文、英文、技术名词、能力描述和场景需求等不同输入都进入同一套意图理解与搜索流程，不为某个示例关键词编写特例。
- 每个有效输入都返回结构化结论状态：`sufficient`、`partial`、`no_match` 或 `needs_clarification`。
- 候选充分时返回最多 3 个真实、不重复、有证据和风险说明的 GitHub 候选；不足 3 个时返回实际合格数量，并解释为什么不足。
- 候选明确区分 `skill` 与普通 `repository`；Skill 必须通过仓库文件或 `SKILL.md` 等证据确认，不能只凭名称猜测。
- Agent 可从工具注册表中选择 GitHub 搜索、仓库元数据、文件树、README、Release、Issue 等工具。
- 每次工具调用有参数校验、结果大小限制、超时、错误观察和轨迹记录。
- Agent 在达到目标、达到步数/预算上限或无法继续时可靠停止。
- 至少有一个合格候选时，用户可选择一个候选深入解析，或对多个候选生成横向比较文章。

### 主要任务

本阶段保留两个关键检查点，不再按单个函数拆课：

1. **工具系统检查点**：定义统一 Tool Schema、工具注册表和执行器；实现 GitHub 搜索、仓库元数据、README/文件检查等确定性工具，并完成参数校验、超时、裁剪和错误结构。
2. **Agent 产品检查点**：实现 `目标理解 → 查询改写/扩展 → 多轮搜索 → 调工具补证据 → 过滤/排序 → 形成结论` 循环，以及最大轮数、预算、取消、轨迹和候选结果页面。

搜索意图至少包含用户目标、可选的候选类型、技术约束和场景约束。查询改写可进行中英文转换、同义词扩展和 GitHub 搜索限定，但必须保存原始输入与实际查询，便于回放。

候选排序先使用可解释的混合方法：硬性过滤由程序完成，相关性、文档质量、活跃度、许可证和风险形成结构化特征；模型负责语义判断和解释，不能单独决定真实链接或基础事实。没有足够证据时输出无结果或澄清结论，不强制推荐。

### 知识点

- Function Calling、JSON Schema、Tool Result 与 Observation。
- Agent Loop、停止条件、上下文膨胀和工具错误恢复。
- 自主性与确定性的权衡；何时直接调用工具比交给模型更合适。
- 搜索召回、候选过滤、Learning to Rank 的基础思想，以及事实特征与模型判断的组合。
- Query Understanding、Query Rewriting、Query Expansion，以及搜索结果不足时的澄清与拒答策略。

### 注意事项

- 先确认当前智谱模型的工具调用能力和返回协议；必要时做 Provider 适配层。
- 工具必须白名单化，不能允许模型构造任意 URL 或执行任意代码。
- 对工具输出做裁剪和结构化，避免 README/Issue 填满上下文。
- GitHub 搜索结果不是质量证明；Star 只能作为弱信号，不能替代相关性、文档、维护状态和许可证检查。
- Fork、镜像和同一方案的不同入口需要去重；归档、长期未更新和缺少许可证必须显式标注。
- “支持任意关键词输入”表示所有有效输入都能被处理并得到结论，不表示 GitHub 必然存在相关项目，也不表示系统需要回答与 GitHub 解决方案无关的通用知识问题。

### 验收标准

- 测试集覆盖中文、英文、宽泛需求、精确技术词、冷门需求、歧义输入和预期无结果输入，不存在为单个示例关键词定制的分支。
- 每个有效输入都返回可解释的结构化结论；有充分结果时最多返回 3 个候选，没有充分结果时不凑数。
- 每个候选包含 URL、类型、推荐理由、证据、适用场景、局限和维护风险。
- 非法参数不会触发真实 GitHub 请求。
- 达到最大步数、超时和上游失败时能可控结束并提供诊断。
- 轨迹可回放，且最终结论能够关联到工具证据。
- 达到 `product-metrics.md` 中查询处理覆盖率、结论可追溯率、候选相关性、链接有效率和无结果诚实率的初始目标。

## 阶段 4：有界的研究—写作—评审编排

**状态：未开始**

### 阶段目标

把仓库研究和关键词发现两种入口统一到有显式状态、质量关卡和人工审批的受控工作流，而不是无限自治的黑盒。

### 期望输出

- 形成收集证据、研究、写作、评审、按需修订的可视化流程。
- 只有评审不通过时才修订，并受到轮数、token、时间和费用预算限制。
- 中间状态可持久化或重放，单节点失败可以重试。

### 主要任务

1. 定义工作流状态、两种入口的路由、节点输入输出和状态转换。
2. 分离 Researcher、Writer、Critic 的 Prompt 和权限，但第一版不引入自由对话式多 Agent。
3. 实现条件路由、最多一次自动修订、重试策略和全局预算。
4. 对独立平台写作使用并行，对共享证据和候选数据保持单一来源。
5. 增加人工审批节点，避免低质量内容自动进入下一环节。

### 知识点

- Workflow、Router、Planner、Critic 与 Agent 的边界。
- 状态机/DAG、幂等性、检查点、并行和补偿。
- 多角色协作的收益、上下文成本和错误传播。

### 验收标准

- 流程分支、重试和停止条件有自动测试。
- Critic 能给出结构化问题，修订前后可以比较。
- 任一节点失败不会丢失之前成功的结果。
- 预算耗尽时安全停止，不发生无限循环。
- 自动评审和修订必须在固定评估集上证明可用成果率提高，否则删除该复杂环节。

## 阶段 5：内容记忆与 RAG

**状态：未开始**

### 阶段目标

让 Agent 利用历史研究、已发布内容和写作规范，同时保持来源清晰和内容新鲜度。

### 期望输出

- 保存研究记录、草稿、人工修改和最终版本。
- 根据当前仓库与平台检索相关历史内容或写作规范。
- 生成内容能标明使用了哪些检索片段，并避免复制历史文章。

### 主要任务

1. 设计会话状态、长期记忆和业务数据库的边界。
2. 先实现按项目类型、平台、标签和关键词的普通检索，建立无向量基线。
3. 在历史内容数量和评估结果证明有需要后，再选择向量存储并建立分块、Embedding 管道。
4. 实现元数据过滤、相似度检索、Top-K 和上下文预算。
5. 把检索结果作为带来源的数据注入 Prompt，记录引用关系。
6. 利用人工编辑前后差异形成风格偏好，但提供关闭和清除机制。

### 知识点

- 短期记忆、长期记忆与 RAG 的区别。
- Chunking、Embedding、向量检索、混合检索和 rerank。
- 召回率/精确率、上下文污染、陈旧信息和引用追踪。

### 验收标准

- 检索测试集能衡量相关片段是否进入 Top-K。
- 关闭 RAG 后系统仍可降级生成。
- 每个检索片段有来源与更新时间，可删除和重建索引。
- 不因历史文章相似而直接复制大段内容。
- 只有在固定检索集和内容质量指标上优于普通检索，才保留向量检索复杂度。

## 阶段 6：安全、合规与可靠性

**状态：未开始**

### 阶段目标

系统化防御不可信仓库内容、工具滥用、资源消耗和内容合规风险。

### 期望输出

- 针对 Prompt Injection、非法工具参数、超大输入和滥用请求建立防护。
- 形成安全测试清单、威胁模型和故障降级策略。
- 最终内容保留事实来源、风险提示和必要的版权/引用信息。

### 主要任务

1. 建立数据与指令隔离，测试恶意 README 对 Agent 的影响。
2. 实现工具白名单、参数 Schema、域名限制、超时、内容长度和调用预算。
3. 增加鉴权、限流、缓存、重试退避和熔断/降级。
4. 检查密钥、日志脱敏、数据保留、用户删除和错误暴露。
5. 制定生成内容的引用、版权、免责声明与人工审核规则。

### 知识点

- Prompt Injection、间接注入、数据外泄和越权工具调用。
- Least Privilege、Defense in Depth、速率限制和供应商故障隔离。
- 生成式内容的来源透明度与人工责任边界。

### 验收标准

- 安全样例无法让 README 覆盖 System Prompt 或调用未授权工具。
- 超时、限流、模型繁忙和 GitHub 失败均有可预测响应。
- 浏览器端、仓库和日志中均不出现密钥。
- 威胁模型和关键防护有自动化测试或可复现验证步骤。

## 阶段 7：Human-in-the-loop 产品体验

**状态：未开始**

### 阶段目标

让用户理解 Agent 正在做什么、能控制结果并能从失败中恢复。

### 期望输出

- 页面展示阶段进度和精简工具轨迹，而不是长时间无反馈。
- 用户可以编辑、批准、拒绝、局部重试或只重新生成一个平台。
- 保存版本和人工修改，支持回看与比较。

### 主要任务

1. 设计 Agent 运行状态、流式事件和取消机制。
2. 实现分阶段进度、引用/证据查看和友好错误恢复。
3. 提供公众号与小红书独立编辑、复制、重生成和审批。
4. 实现历史记录、版本差异和恢复。
5. 用真实任务进行可用性测试，减少等待焦虑和错误操作。

### 知识点

- Streaming、事件模型、乐观/悲观状态和可取消任务。
- Human-in-the-loop、可解释性、信任校准与审批门。
- Agent 产品中的部分成功、局部重试和恢复设计。

### 验收标准

- 用户能看到当前阶段并取消长任务。
- 一个平台失败不必重新运行全部流程。
- 人工修改不会被意外覆盖，版本可比较和恢复。
- 错误提示包含可执行的下一步，但不泄露服务端细节。
