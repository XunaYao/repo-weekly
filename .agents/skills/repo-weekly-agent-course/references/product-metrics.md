## 使用原则

- 每个阶段至少选择一个质量指标、一个可靠性指标和一个效率指标。
- 没有真实样本时先实现采集并记录基线；初始目标用于课程验收，积累 20 次以上真实任务后再校准。
- 同时保存总量、成功量、失败原因和样本链接，不能只保存平均值。
- 区分模型质量问题、工具/网络失败、解析失败和用户主动取消。
- 指标用于发现退化和比较方案，不为了达标隐藏失败样本。

## 北极星指标

### 可用成果率

定义：用户认为无需重写、只需轻量修改即可使用的最终成果数 ÷ 已完成任务数。

- 阶段 1～2 初始目标：≥ 60%。
- 阶段 4 完成目标：≥ 75%。
- 生产目标：≥ 85%。

“可用”必须由用户确认，不能只由模型自评。仓库文章和关键词推荐文章分别统计。

### 有效任务完成率

定义：在预算和超时限制内得到结构合法、页面可消费结果的任务数 ÷ 有效请求数。

- 原型目标：≥ 90%。
- 生产目标：≥ 97%。

模型供应商整体故障需要单独统计，但不能从总失败记录中删除。

## 内容质量指标

| 指标               | 定义                                                                 | 初始目标     |
| ------------------ | -------------------------------------------------------------------- | ------------ |
| 结构校验通过率     | 首次模型输出通过运行时 Schema 的次数 ÷ 模型成功响应次数              | ≥ 95%        |
| 关键结论证据覆盖率 | 能关联仓库、README、Release、Issue 等证据的关键结论数 ÷ 关键结论总数 | ≥ 90%        |
| 严重无依据陈述数   | 与来源冲突或完全无来源的关键事实                                     | 每篇 0 条    |
| 平台适配合格率     | 人工量表确认结构、语气和篇幅适合目标平台的草稿比例                   | ≥ 80%        |
| 轻量编辑比例       | 用户修改字符数 ÷ 原草稿字符数；结构性重写单独标记                    | 中位数 ≤ 30% |

## 可靠性、效率和成本指标

| 指标             | 定义                                                              | 初始目标                           |
| ---------------- | ----------------------------------------------------------------- | ---------------------------------- |
| API 技术成功率   | 返回预期成功结构的 API 请求数 ÷ 有效请求数                        | ≥ 95%                              |
| 错误可分类率     | 能归类为输入、GitHub、模型、解析、预算、超时或取消的失败比例      | 100%                               |
| 重试恢复率       | 可重试故障在一次受控重试后恢复的比例                              | 先建基线，目标 ≥ 70%               |
| 首次结果延迟     | 从提交到首次完整可用结果的 P50/P95                                | 阶段 1 先建基线；生产 P95 ≤ 180 秒 |
| 单任务模型调用数 | 一次任务中的模型调用总数，按流程节点拆分                          | 每阶段设预算，不允许无上限         |
| 单任务工具调用数 | 一次 Agent 任务执行的 GitHub 工具总数                             | 阶段 3 建基线并设置最大轮数        |
| Token/费用       | 输入、输出 token 与供应商费用；供应商不返回时记录估算或标记不可得 | 每次运行可追溯                     |

## GitHub 解决方案发现指标

适用于“输入任意有效自然语言关键词或需求，搜索 GitHub Skill/代码库并形成结论”的模式。结果状态为 `sufficient`、`partial`、`no_match` 或 `needs_clarification`；候选充分时最多返回 3 个，不为凑数降低门槛。

| 指标               | 定义                                                                    | 初始目标             |
| ------------------ | ----------------------------------------------------------------------- | -------------------- |
| 查询处理覆盖率     | 有效非空输入得到结构化结论状态的比例                                    | 100%                 |
| 结论可追溯率       | 结论可关联原始输入、实际搜索查询和 GitHub 证据的比例                    | 100%                 |
| 合格候选充足率     | 能找到 3 个合格候选的查询比例；用于了解 GitHub 供给，不作为强制质量门槛 | 先建基线             |
| 返回候选相关性     | 人工判断相关的候选数 ÷ 实际返回候选数                                   | ≥ 80%                |
| 至少一个可用候选率 | 返回候选中至少一个被用户选为可尝试方案的查询比例                        | ≥ 80%                |
| 链接有效率         | 推荐项的 GitHub URL 可访问且与展示项目一致的比例                        | 100%                 |
| 证据完整率         | 推荐理由包含可验证 README/元数据/文件证据的候选比例                     | 100%                 |
| 重复候选率         | 同仓库、Fork 或实质重复方案在同次结果中重复出现的比例                   | 0%                   |
| 维护风险标注率     | 归档、长期未更新、许可证缺失等风险被正确标注的比例                      | 100%                 |
| 无结果诚实率       | 预期无合格候选的测试中返回 `no_match`/`partial` 而非低质凑数的比例      | 100%                 |
| 查询改写有效率     | 原查询无合格结果时，经合理改写后找到相关候选或给出正确无结果结论的比例  | 先建基线             |
| 推荐到文章完成率   | 至少有一个候选后继续完成解析和文章生成的任务比例                        | 先建基线，目标 ≥ 60% |

## RAG 指标

在积累足够历史内容之前不启用向量检索。先用元数据和关键词建立基线，再决定是否增加 Embedding。

| 指标           | 定义                                       | 初始目标               |
| -------------- | ------------------------------------------ | ---------------------- |
| Recall@K       | 标注相关片段出现在前 K 个结果中的查询比例  | 在固定检索集上 ≥ 80%   |
| 引用准确率     | 生成内容对检索片段的引用与原文一致的比例   | ≥ 95%                  |
| 无效检索注入率 | 与当前任务无关却进入最终 Prompt 的片段比例 | ≤ 10%                  |
| RAG 增益       | 开启 RAG 相比关闭 RAG 的可用成果率变化     | 必须为正才保留复杂方案 |

## 采集时机

1. 阶段 1：记录结构成功率、错误分类、延迟和用户可用反馈。
2. 阶段 2：建立固定样例集，记录内容质量、Prompt 版本、模型、token 与费用。
3. 阶段 3：增加原始输入、查询改写、结论状态、候选、工具调用、相关性和选择反馈。
4. 阶段 4：增加节点耗时、评审通过率、修订次数和修订增益。
5. 阶段 5：增加检索指标，并用无 RAG 基线证明增益。
6. 阶段 6～8：形成监控面板、告警阈值和发布质量门禁。
