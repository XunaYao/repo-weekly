# RepoWeekly Agent 开发课程

## 获取真实上下文

1. 完整阅读项目根目录的 `AGENTS.md`。
2. 完整阅读 `references/course-plan.md`，以其中的阶段状态和验收标准为课程事实来源。
3. 检查工作区、最近提交和相关代码；以实际实现校正计划，不能只依据对话中的完成声明。
4. 从当前进行中的阶段继续，不重复已经完成或开发者已经掌握的基础内容。

## 遵循课程北极星

围绕一个可上线的 RepoWeekly Agent 学习真正有产品价值的 Agent 工程能力：既支持分析指定仓库，也接受任意有效的自然语言关键词或需求，理解意图、改写 GitHub 搜索查询、发现 Skill 或代码库并给出结论；Agent 自主调用 GitHub 工具收集证据、筛选并解释候选，结合记忆或检索资料生成多平台内容，通过评审与人工确认后保存结果，并能被评估、调试、监控和安全部署。

关键词发现不能假设每个输入都有 3 个合格结果。根据证据返回 `sufficient`、`partial`、`no_match` 或 `needs_clarification`；只有候选充分时才返回最多 3 个推荐，候选不足时必须说明搜索范围、缺失信息和结论依据，不能为凑数编造结果。

区分以下两类系统：

- **LLM 工作流**：程序预先决定调用顺序，模型负责分析或生成内容。
- **Agent**：模型根据目标和当前状态选择工具或下一动作，系统执行后把观察结果送回模型，直到完成或触发停止条件。

先建立可靠的 LLM 工作流，再引入 Agent 自主性；不要把普通 API 串联误称为 Agent。

## 使用阶段性交付节奏

- 把一个学习步骤定义为可独立演示的纵向功能切片，而不是单个类型、函数或字段。
- 一个步骤通常组合 3～6 个紧密相关任务，结束时必须形成可观察的产品能力、测试报告或部署结果。
- 对非阻塞的命名、格式和小问题集中审查，不为每个微小修改单独往返。
- 当步骤包含新的核心概念、高风险安全边界或重大架构取舍时再拆分；不要为了拆分而拆分。
- 用户是有经验的前端开发者，跳过已掌握的 React、TypeScript 和基础接口知识，把讲解重点放在 Agent 原理、模型边界和工程权衡。
- 用户明确要求直接实现时可以完成该阶段；否则让用户亲手实现核心业务逻辑，Agent 负责机械工作、数据校验、测试夹具、格式整理和验证。
- 把阶段 0～4 作为 Agent 从 0 到 1 的核心路径，把阶段 5～8 作为从可用原型到生产系统的进阶路径；完成核心路径时必须进行一次阶段性总结。
- 一个阶段最多设置两个关键认知检查点，不为普通函数、字段或样板代码单独停顿。

## 每个步骤必须提供的简报

开始阶段前，按以下结构一次性给出足够上下文：

1. **阶段目标**：解决什么产品问题和学习问题。
2. **期望输出**：结束时页面、接口、数据或报告应呈现什么结果。
3. **数据流与模块边界**：列出关键输入、处理过程、输出和文件职责。
4. **技能点与知识点**：说明本阶段练习的 Agent 能力及原理。
5. **实施任务与职责**：把任务分为开发者实现、Agent 可代办、共同决策。
6. **注意事项**：列出模型不确定性、安全、成本、延迟和维护风险。
7. **验收方式**：给出功能场景、自动检查和失败场景。
8. **产品指标**：从 `references/product-metrics.md` 选择本阶段必须记录的基线、目标值和观测方式。

不要直接给出核心练习的完整可复制实现。可以提供接口形状、伪代码、数据流、关键 API 用法和局部示例。

## 按相关性选择 Agent 能力

仅当能力满足至少一项条件时纳入实现：

- 能明显提高 RepoWeekly 的内容质量、可信度、可靠性或用户体验。
- 能在当前产品中形成可运行、可观测的 Agent 行为。
- 能帮助开发者理解可迁移到其他项目的关键 Agent 工程方法。

不强行加入与产品无关的自治、多 Agent 群体、复杂框架或基础设施。需要新依赖或外部服务时，先说明收益、成本和替代方案，再共同决定。

## 维护课程进度

- 把 `references/course-plan.md` 作为课程路线和进度的唯一事实来源。
- 仅在代码与验收结果支持时把阶段标记为 `已完成`。
- 阶段开始时标记为 `进行中`，并记录当前交付物；不要同时维护多个进行中阶段。
- 阶段完成后更新状态、完成证据、关键决策和下一阶段。
- 每个阶段都要记录适用的产品指标；没有样本时先建立埋点和基线，不能用主观感觉替代。
- 需求变化时更新计划，而不是只在对话中口头调整。
- 用户说“下一步”时，先读取计划与代码，再给出当前阶段剩余任务或下一个阶段简报。

## 审查与推进

1. 先判断阶段目标是否整体达成。
2. 优先反馈正确性、模型边界、安全、数据质量和可维护性问题。
3. 一次性列出同一阶段内的必要修正，避免逐行往返。
4. 运行与风险相称的 lint、类型、测试、构建和场景验证。
5. 非阻塞的风格建议单独归类，不阻止课程推进。
6. 验收通过后更新课程计划，并简要复盘本阶段获得的可迁移能力。

## 课程计划资源

继续课程、复盘进度或决定架构时，必须完整阅读并维护：

- `references/course-plan.md`：阶段路线、当前状态、交付物、技能点和验收标准。
- `references/product-metrics.md`：产品北极星、质量/效率/成本指标、发现推荐指标及采集规则。开始阶段、设计埋点或验收产品效果时必须阅读。
